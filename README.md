# nixos

Personal NixOS + Home Manager configuration, built as a flake. Manages a NixOS
laptop today; structured so a second machine (a host, or a standalone
Home Manager setup like WSL) is cheap to add later.

## Structure

```
flake.nix, flake.lock        entry point: wires everything below together
lib/
  mksystem.nix                hostname -> nixosConfigurations.<hostname>
  mkhome.nix                  { username } -> homeConfigurations.<username> (standalone HM, e.g. WSL)
hosts/<name>/                 one NixOS system config per machine
  default.nix                 hardware-specific + machine-specific bits
  hardware-configuration.nix  generated by nixos-generate-config, don't hand-edit
home/<name>/                  one Home Manager config per person/context
  default.nix
modules/
  nixos/                      reusable NixOS-level pieces
    common.nix                 applies to every host
    desktop/                   desktop-environment-specific (gnome.nix, ...)
  home-manager/                reusable Home Manager pieces
    common.nix                  applies to every home (fonts, etc.)
    desktop/                    GUI apps (alacritty.nix, gnome.nix dconf tweaks)
    development/<tool>/         one dir per dev tool
      default.nix                 the actual config
      files/                      vendored raw config files (lua, kdl, ...)
```

## Structure Motivation

- **`hosts/` and `home/` are thin.** Each file there is just "which modules
  does this specific machine/person want," plus the handful of settings that
  genuinely can't be shared (hostname, LUKS UUIDs, username, git identity).
  Everything reusable lives in `modules/` so a second host or home mostly
  just picks from the same shelf instead of copy-pasting.
- **`modules/nixos` vs `modules/home-manager` mirrors the real split**
  between what NixOS manages system-wide (users, boot, desktop manager) and
  what Home Manager manages per-user (dotfiles, shell, dev tools) — see
  [NixOS vs Home Manager](https://nix-community.github.io/home-manager/index.html#ch-nixos)
  if that boundary is unclear.
- **`lib/mksystem.nix` / `lib/mkhome.nix`** exist so `flake.nix` stays a thin
  list of `mkSystem "hostname"` / `mkHome { username = "..."; }` calls as
  more hosts/homes get added, instead of the boilerplate growing inline.
- **`development/<tool>/files/`** holds real vendored files (e.g. the neovim
  lua config, the zellij theme) rather than everything being generated from
  Nix strings — easier to read/edit, and lets you drop in upstream files
  (like a theme pulled from a project's own repo) with zero translation.

## How things are tackled

- **New files must be `git add`ed before Nix can see them.** Flakes only
  look at git-tracked content; a brand-new file that isn't staged yet will
  make `nix build`/`nixos-rebuild` fail with a "not tracked by Git" error
  that has nothing to do with the file's content. Stage first, then build.
- **Validate before switching:**
  ```
  nix flake check --no-build
  nix build .#nixosConfigurations.<host>.config.system.build.toplevel
  ```
- **Apply on NixOS:** `sudo nixos-rebuild switch --flake .#<host>`
- **Apply standalone Home Manager (e.g. WSL):**
  `home-manager switch --flake .#<username>`
- **Shared defaults use `lib.mkDefault`** (see `zellij/default.nix`'s
  `default_shell`) so a module usable by multiple homes has a sensible
  default that any one home can override with a plain assignment, no
  `lib.mkForce` needed.
